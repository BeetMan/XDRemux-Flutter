# 内置局域网文件传输开发计划

日期：2026-10-21。状态：P2.0–P2.3 的 Windows/Android 文件互传功能与首轮验收完成：手动直连、自动发现、显式重试、收件箱、独立 ABI 1.3 及 release 打包。2 GiB/1000 文件原生规模复验通过；P3.0 已通过最终 Windows release 传输组件与官方 Android LocalSend 1.18.2 双向五文件及发现验收；P3.1 已修复停止状态、多播锁清理和 Windows 独占端口错误提示，Windows／Android release 受控故障与恢复、26 core／2 ABI／80 Flutter 测试通过，Android 真机多播锁释放／恢复与同端口重启通过。P3.2 真实网络／平台矩阵待验，Apple 待验，鸿蒙验证延后。

## 目标与开发基线

将照片原文件可靠地传到另一台设备，减少系统分享对 HEIC、私有尾部、人像辅助图像和动态照片资源的改写。支持 XDRemux 与 LocalSend 文件互传，并为 XDRemux 间的照片资源分组和往返工作流保留扩展能力。

- 分支：`codex/local-transfer`；独立工作树开发。
- 起点：`integrate/huawei-portrait-live` 的已提交版本 `877047b87fda65ca5d8cc6bce3aa591ed1efd111`。
- 原工作区未提交的 codec、界面、网站及鸿蒙原生代码不纳入本分支。开始接入应用前，先检查这些工作是否已合入，按需更新基线。
- P0 使用隔离 harness；P1 新增独立 `crates/xdremux-transfer`，P2.0 新增 `crates/xdremux-transfer-ffi`；图像引擎、Flutter 应用、默认依赖与发布配置保持独立。用户已要求推送开发分支；发布与主线合并仍另行安排。
- 技术依据为 2026-10-15 的只读调研；开始 PoC 时重新核对上游版本、协议及平台要求，并记录实际提交哈希。

## 首版范围

首版提供：发送已导入的原文件或转换结果、设备发现、手动 IP/端口、明确的接收确认、接收箱、批量进度、取消和失败文件重试。默认使用 HTTPS，接收完成后再交给转换队列或文件导出。

区分四类结果：网络传输完成、文件校验完成、图库写入完成、目标图库功能验收通过。不能用其中一项替代其他项。哈希一致只说明发送与接收字节相同，不能证明系统选择器提供的是完整原始资产。

首版不包含公网穿透、云中转、账号、目录同步、浏览器收发、通用断点续传、永久后台接收和无人确认自动接收。Live Photo 成组导入及 Apple/OPPO 往返任务关联安排在后续阶段，不作为文件互传首版的隐含承诺。

## 架构与选型原则

优先评估封装 LocalSend 独立 Rust 核心，保持 v2 文件互操作；若其嵌入、依赖或目标平台成本过高，再评估独立实现兼容协议。最终选型由 P0 的编译与互操作证据决定，不预先把仓库内部 crate 当作稳定 SDK。

建议的数据流：

`本地文件快照 → 发送会话 → 临时接收文件 → 校验与提交 → 接收箱 → 加入转换队列 / 文件导出 / 后续图库导入`

- 传输逻辑放入独立 Rust crate 候选 `crates/xdremux-transfer/`，不与 HDR、人像、编码器逻辑耦合。
- Flutter 侧采用独立服务与状态模型，避免把协议实现放进 `main.dart`；具体界面入口在 P2 确认。
- 是否复用现有动态库或单独打包，在 P0 根据可选依赖、体积与平台构建影响决定。关闭功能时不得要求图像引擎初始化网络服务。
- 延续现有 C ABI 和内存管理纪律，不为此全局迁移桥接框架。长生命周期服务使用独立 runtime/工作线程，桥接暴露短调用和有界事件队列；UI 主 isolate 不承担阻塞 I/O。
- 会话、传输和事件使用稳定 ID；定义事件顺序、取消幂等性、服务关闭、句柄释放和 ABI 版本检查。错误用稳定错误码，不依赖异常字符串匹配。
- 普通 LocalSend 对端只使用标准文件语义；XDRemux 资源分组另行协商，不能假设普通客户端理解自有清单。

### P1：可独立运行的传输服务

- [x] 实现服务启停、地址绑定、会话协商、接收决策、逐文件发送、取消、进度和错误模型。
- [x] 流式读写、有界并发和事件背压；不把整批文件读入内存。
- [x] 发送前固定可读源文件快照，检查长度/修改变化；必要时复制到稳定暂存区，避免计算哈希后源文件变化。
- [x] 接收至临时文件；检查声明长度、实际长度和可用哈希后再提交。校验失败不进入接收箱或转换队列。
- [x] 自有客户端发送 SHA-256；接收第三方无哈希文件时记录“长度已核对、无对端哈希”，不能显示为已完成端到端哈希校验。
- [x] 约束文件数、声明体积、元数据和路径长度；校验磁盘空间，拒绝路径穿越、绝对路径及越界链接，明确重名策略。
- [x] 实现会话超时、取消清理、进程重启后的临时文件清理和失败文件重试。
- [x] 默认显式接收确认；校验证书身份，禁用未经用户选择的明文降级；不把同名设备视为同一可信身份。
- [x] 日志不记录文件内容、PIN、会话 token 和完整私人路径。

2026-10-18 记录：[P1 验证](../testing/local-transfer-p1.md)。15 项核心测试（含本机 HTTPS）、Windows junction 防护及两平台 release 构建通过；用户放行防火墙、手机重新连接后，Windows ↔ Android 双向复验完成，各 5 文件、18,579,897 bytes，独立磁盘长度/哈希一致。

退出条件：独立 harness 通过成功、拒绝、取消、超时、空间不足、错误哈希、截断输入及路径攻击用例；重启后不会把残缺文件识别为成功文件。

## 验收矩阵与证据

| 维度 | 最低覆盖 | 证据 |
|---|---|---|
| 文件保真 | JPEG、普通 HEIC、带私有尾部/人像数据 HEIC、MOV、正确 Live Photo 双文件 | 两端长度与 SHA-256；输入文件保持不变 |
| 批次与性能 | 单文件 ≥2 GiB、至少 1000 个小文件、照片混合批次 | 文件清单、用时、峰值内存/CPU和网络信息；文件增大时内存不按文件大小线性增长 |
| 生命周期 | 取消、退出、进程被杀、锁屏、退后台、网络断开/切换、恢复重试 | 文件与会话终态、临时文件清理、重复/覆盖行为 |
| 文件系统 | 中文、emoji、重名、路径边界、磁盘不足、无权限 | 错误码与用户提示；既有文件不被意外覆盖 |
| 网络与权限 | 权限拒绝/撤销、VPN、多网卡、端口冲突、多播失败、AP 隔离 | 发现/直连分别记录，失败原因与兜底路径 |
| 互操作 | XDRemux ↔ XDRemux；XDRemux ↔ 选定 LocalSend 版本 | 双方向、平台/客户端版本、文件清单和校验结果 |
| 图库与回归 | 文件保存、后续 Live Photo 导入、现有转换和系统分享 | 分开记录传输与图库结果；真实目标图库验证 |

测试分层：Rust 覆盖会话、流式写入、路径/体积约束、校验和取消；桥接覆盖句柄释放、事件顺序及并发；Flutter 覆盖接收确认、进度、重试和队列交接；真实设备负责权限、多播、后台限制、跨客户端及图库行为。性能阈值在 P0 测量后确定，不使用未经测量的速度承诺。

建议验证记录落在 `docs/testing/local-transfer-validation.md`，以“未执行/通过/失败/受阻”记录每项，不以文档存在代表验证通过。

## 第一轮执行顺序

1. 完成 P0：锁定上游、建立独立 harness、Windows/Android 双向互传，尽早排查 Apple 与鸿蒙目标。
2. 根据 P0 证据定核心复用与 ABI 方案，再实施 P1。
3. 先完成 P2 的文件收发闭环，再收敛 P3 各平台体验。
4. 协调已有 Live Photo 与鸿蒙原生开发后推进 P4；最后完成 P5。
