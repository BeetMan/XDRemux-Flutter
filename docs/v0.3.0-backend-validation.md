## main 同步记录

已读取并同步 `origin/main` 的 v0.2.8 功能性更新（`b3aadae`、`f2d954c`）：移除顶栏 OPPO 快捷开关，将 HDR family、OPPO 兼容、相机尾部和严格 tmap 收入默认折叠的“高级模式”，并保留 v0.2.8 release notes。v0.3.0 的 Flutter/Rust/Installer 版本号未回退，P0.0 Swift backend 选项保留在 Apple 平台设置中。

## P0.0 已完成

- 新增 `ConversionBackend.rust` / `ConversionBackend.swift`；Rust 是默认值。
- 新增统一 request、progress、cancellation、error、output-validation contract。
- Rust adapter 保留原 FFI 参数、进度 handle、后台 isolate 和硬件编码路径。
- macOS/iOS 通过 `xdremux/swift-backend` MethodChannel 暴露 capability probe。
- Swift 选项仅在 macOS/iOS 显示；Windows/Android 不显示。
- Swift capability 在未接入原生包的构建中明确为 unavailable；不会把“可见”误报为“可用”。
- 未添加 Swift CLI 子进程路径；P0.2 仅在 macOS Swift 后端按 capability 开放 Photographic Styles，Apple Portrait 仍关闭。

取消语义目前是 best-effort：Rust FFI 没有中断原语，因此取消中的 Rust 调用会继续运行到 native 返回，Flutter 不会再把其结果标记为“已转换”。Swift 也沿用同一个 request id；上游 Core 当前没有可注入的硬中断点。

## P0.1 已接入（macOS Swift 标准 HDR）

- `apps/flutter/macos/SwiftBackend/Package.swift` 以 exact `1.3.1` 依赖上游 `XDRemuxCore` / `XDRemuxAppleFeatures`，没有合并 upstream 历史。
- `XDRemuxFlutterBackend` 直接调用 `ConversionEngine.convert` 和 `ConversionEngine.isValidOutput`；没有启动 Swift CLI、读取 stdout 或解析 CLI 文本。
- `Runner/AppDelegate.swift` 通过 `xdremux/swift-backend` MethodChannel 调用 Swift Library，并通过 `xdremux/swift-backend/progress` EventChannel 转发统一进度事件。
- Swift capability 当前报告 `swiftStandardHdr=true`、`swiftPhotographicStyles=true`、`swiftPortrait=false`；Photographic Styles 仍显示实验性警告，Portrait 不显示。
- Swift 后端的输出在原生侧先做 ISO gain-map 验证，Dart 侧再执行统一输出验证；失败不会标记为已转换。
- 批次完成时显示实际选择的后端；Swift 转换错误会在队列项和批次提示中明确标记为 Swift 后端错误。
- Swift 后端只在 macOS 接入。iOS 仍保留 capability gating，不链接这个 macOS-only package，也不启动 Swift CLI。
- iOS 的 `xdremux/swift-backend` 当前仅返回明确的 unavailable capability stub；不会伪装成 Swift Core 或 AppleFeatures 已支持。

## macOS deployment target 评估

在 P0.1 接入前，Flutter macOS 工程的三个层面是 macOS 12：

- `apps/flutter/macos/Podfile`：`platform :osx, '12.0'`
- `apps/flutter/macos/Podfile` 的 `post_install`：Pods target 写入 `MACOSX_DEPLOYMENT_TARGET = '12.0'`
- `apps/flutter/macos/Runner.xcodeproj/project.pbxproj`：Runner Debug/Profile/Release 均为 `MACOSX_DEPLOYMENT_TARGET = 12.0`

上游 `v1.3.1` 的 `Package.swift` 明确声明 `.macOS(.v15)`。macOS 12 不能被视为兼容配置，因此本阶段已将以下配置统一提升到 macOS 15：

- `apps/flutter/macos/Podfile` 的 `platform :osx`；
- `Podfile` 的 `post_install` 生成的 `MACOSX_DEPLOYMENT_TARGET`；
- `Runner.xcodeproj` 的 Debug/Profile/Release 项目级 deployment target。

原生 Package resolve 和 Swift Package 编译已验证通过；CocoaPods 安装后，arm64 Flutter Runner 已完成最终链接；universal 目标仍受上游 x86_64 `Float16` 编译问题阻断。

即使提升到 macOS 15，也不能据此开放 iOS：上游 Core 使用 `Process`/`xcrun`，Portrait 使用外部 `zstd`，AppleFeatures 使用 Vision/CoreImage 及原生辅助资源，需单独做 iOS 编译与运行时 capability 验证。

## P0.2 AppleFeatures 接入状态

已将上游 `XDRemuxAppleFeatures` SwiftPM product 接入 macOS bridge，并让统一请求携带 `applePhotographicStyles` / `applePortrait`。原生转换在 Apple 功能请求下直接调用 `AppleFeatureConversionEngine`，随后使用上游 Apple 输出验证器，而不是用 Rust validator 代替；OPPO-compatible 请求仍由上游和 Flutter 双侧拒绝/清除。

当前 Photographic Styles capability 已通过一个版本化 resource compatibility overlay 开放，但仍保留实验性警告和单文件失败处理。Overlay 将上游 helper 对旧的 `initWithURL:type:image:useEmbeddedPreview:` 调用适配到当前系统提供的 `initWithURL:type:useEmbeddedPreview:`，只写入 app cache，不修改 SwiftPM checkout。

## 未宣称的能力

当前 P0.1 已完成 macOS 原生 Swift Library 接入，以及同一批真实样例的双后端有效输出验证；现有 iOS Rust 路径也已完成 debug device build，但 iOS Swift Core 尚未嵌入，Apple 功能没有开放。仍未宣称“Swift/Rust 输出等价”，也未完成 Apple Photos 导入流程。P0.2 的 Photographic Styles bridge、兼容层和结构验证已接入并按实验性能力开放；Portrait 仍因 zstd/真实输入验证不足而关闭。当前 arm64 Runner 已完成最终链接；universal 构建仍需处理上游 `XDRemuxCore` 在当前 Xcode beta x86_64 路径的 `Float16` 兼容性，之后再记录 Photos 导入、编辑、保存、退出和重新打开结果。

已读取上游 `21Z121Z1/XDRemux` 的 `v1.3.1` tag（commit `6d99b568`）：其 `Package.swift` 当前只声明 `.macOS(.v15)`，并将 `XDRemuxCore`、`XDRemuxAppleFeatures` 和 CLI 分成 SwiftPM targets。本阶段只通过固定版本 SwiftPM 依赖接入这两个 Library product，没有把上游独立历史整体合并，也没有将 macOS-only 源码误标为 iOS 可用。

## OPPO watermark isolation prototype（未开放）

针对 OPPO 水印被 Photographic Styles 处理的问题，增加了一个仅用于 macOS 实验验证的隐藏开关：

```text
XDREMUX_APPLE_STYLES_ISOLATE_OPPO_WATERMARK=1
```

开关只对 Photographic Styles 生效，Portrait、Rust 默认路径和普通 Swift Styles 路径不变。桥接层会识别 OPPO post-mdat manifest，将 watermark 相关资源从临时输入尾部移除，Styles 生成后再把 watermark 资源作为独立尾部恢复到输出；未识别到合法 OPPO watermark manifest 时不改输入，尾部解析异常时失败关闭。原始照片和 SwiftPM upstream checkout 均未修改。

本次使用 `/Users/beet/Desktop/src/IMG20240321181713.heic` 验证：macOS `27.0 (26A5388g)`、Xcode `27.0 beta`、Swift `6.4`、上游 `XDRemux v1.3.1`。转换耗时 `116.951s`，输出 `/tmp/xdremux-p02-watermark-isolated/IMG20240321181713.styles-watermark.heic`，大小 `1,977,582 bytes`，SHA-256 为 `7f1a92e190f4c229f2bcd89b28089358635ea21edb827747a2b7704761be1127`；Swift Apple 输出验证通过，输出中同时存在 `styleMetadata` 和 `watermark*` manifest entries。由 `sips` 解码得到的水印区域像素与本次普通 Styles 输出一致；这只能证明文件结构和当前 macOS 解码结果，不能证明 Apple Photos 在应用 Styles 时会把水印排除在编辑范围之外，仍需把该文件导入 iPhone/Photos 做实际编辑、保存、退出和重新打开验证。

该 prototype 当前不进入 UI，也不作为稳定能力宣称；后续若 iPhone/Photos 验证失败，需要改为在图像层分离并恢复水印区域，而不是继续扩大 tail-only 方案。

## OPPO watermark style-data mask prototype（未开放）

针对 tail-only 方案在 iPhone 上仍被 Styles 改色的问题，新增第二个隐藏实验开关：

```text
XDREMUX_APPLE_STYLES_NEUTRALIZE_OPPO_WATERMARK=1
XDREMUX_APPLE_STYLES_WATERMARK_BOTTOM_ROWS=2
```

该 prototype 不移除输入 tail，而是在 Apple Styles 输出完成后定位 `styleMetadata` binary plist 的 key `1`，将上游当前 `12×9×8` style-data 表中底部两行候选空间块（192 个 polynomial blocks）改成 complete identity。binary plist 长度保持不变，改写后重新读取 key `1`，再执行 Apple 输出验证。它只对带合法 OPPO watermark manifest 的 Photographic Styles 请求生效，未进入 UI，也没有修改 upstream checkout。

使用 `/Users/beet/Desktop/src/IMG20240321181713.heic` 生成的候选输出为 `/tmp/xdremux-p02-watermark-mask/IMG20240321181713.styles-watermark-mask.heic`，大小 `1,928,680 bytes`，SHA-256 为 `378016e08997ca2d24976da93e838941173c16f11f851a754f41da789fbf8c65`。styleMetadata 回读确认 `864` 个 blocks 中有 `192` 个为 identity；`XDRemuxSwiftBackend.verifyOutput(... applePhotographicStyles: true)` 通过，完整 smoke test 耗时 `117.041s`。该文件需要在 iPhone 上实际应用 Styles、保存并重新打开后，才能判断 Apple Photos 是否尊重空间块 identity；在此之前不宣称水印已被隔离。

## Returned-photo watermark writeback prototype（未开放）

由于 `IMG_3323.HEIC` 已经是 iPhone/Photos 展平后的结果，输入侧隔离 tail 或修改 `styleMetadata` 都不能阻止 Photos 对已经烘焙进主图的白色水印区域改色。因此增加双输入 prototype：

- donor：`/Users/beet/Desktop/src/IMG20240321181713.heic`；
- returned photo：`/Users/beet/Downloads/IMG_3323.HEIC`；
- bridge：`AppleReturnedPhotoWritebackBridge`；
- 输出：`/tmp/xdremux-p02-watermark-writeback/IMG20240321181713.watermark-restored.heic`。

bridge 从 donor 的 `watermark.config` 和 PNG header 推导出 `4096×440` 的完整底部画布（顶部 y=`3072`）。它把 donor 的该画布回写到 returned photo 的 raster，因此同时恢复白色背景和 `OPPO Find X7 Ultra / HASSELBLAD` 水印，而不是只恢复透明 PNG。输出编码时保留 returned photo 的 ISO gain map 和 ImageIO metadata，并重新打包 donor 的完整 OPPO footer：`local.hdr.linear.mask`、`local.hdr.meta.data`、`private.emptyspace`、`watermark`、`watermark.config`、`watermark.device`、`watermark.params`。

本次实际验证环境仍为 macOS `27.0 (26A5388g)`、Xcode `27.0 beta`、Swift `6.4`、上游 `XDRemux v1.3.1`。针对性测试通过：


这说明 X8U 后置 Portrait 至少存在第二种 depth 量化变体：资源名称和 canvas 协议仍是 `rear.*`，但不能直接套用当前已验证样本的 rank-to-disparity 参数。暂不把猜测规则写入生产路径，也没有开放 Portrait capability。

### 隔离原型：仅补齐量化字段

在未修改生产 checkout 的临时 Swift Package 副本中，做了一个仅用于研究的 fallback：当 `minimum=0`、`maximum=0`、`exponent=0` 且 rank plane 有实际范围时，临时采用 `0...rankMaximum`、`exponent=1`。该原型没有把 `0x18` 的整数解释写入 production parser，仍保留当前 Float32 解释。

原型运行结果：

- 能完成 focus 选择、Vision（3 requests / 5 masks）、Apple HEIF 写入和 Portrait manifest；
- 生成文件：`/tmp/IMG20260807151235.prototype-quant.heic`；
- `validate-portrait`：`passed=true`，`rend.byteStableRoundTrip=true`，`donorContamination.passed=true`；
- 输出 HEIC 可由 macOS ImageIO 重新读取，尺寸 `4096×3072`；
- 生成日志中的 focus rank 仍为 `0.000`，disparity full span 约为 `0`，因为当前样本的 `0x18` 仍按 Float32 解释为极小值；这证明“只补量化范围”可以打通封装链路，但尚不能证明 Portrait 深度物理参数正确；
- 从 HEIC 转出的预览没有保留原 OPPO 白色上下水印区域，水印回写仍需在后续 output mode / watermark restoration 流程中单独处理。

另一个隔离原型把 `0x18` 按 UInt32 整数 `5` 解释，并同时使用上述量化 fallback。该版本在 REND 生成后被 Apple semantic capability 拒绝，未产生输出。因此目前不能采用“直接把 `0x18` 改成整数 scale”的方案。

结论：这张后置人物样本已经证明可通过一个实验性量化 fallback 进入完整 Apple Portrait 输出链路，但当前 disparity 参数不可信，不能作为稳定功能发布。下一步应收集更多同机型后置人像样本，比较 `0x18`、rank plane、实际焦点和 Apple Photos 行为，再确定正确的 producer variant；同时把水印恢复与 Portrait 输出模式合并验证。

诊断报告 schema 为 `xdremux-portrait-depth-diagnostic-v1`，会读取并报告 `rear.depth`、`rear.depth.config`、`src.image` 资源长度，解压后报告 depth header、rank/hair/portrait/pet plane 统计、`0x18` 的 UInt32/Float32 两种解释、量化字段和校准状态。它还解析 config 的版本、声明处理画布、AF focus 点和 `objectDistance`，并从 `src.image` 解出实际 storage 尺寸，用于避免把 focus 点错误地映射到声明的 900×1200 processing canvas。当前四张 X8U 样本均被识别为 `rear-v4-zero-quantization`，`safeToTransform=false`，不会因为诊断成功而进入 Portrait 转换。

诊断层只在 macOS wrapper 中使用本机已安装的 zstd（当前验证路径为 `/opt/homebrew/bin/zstd`）；它不是 iOS 能力，也没有改变 `swiftPortrait` capability。当前主机上的 capability 语义是：`swiftPortraitDiagnostic=true`、`swiftPortrait=false`。因此不会把外部 zstd 或猜测性 disparity 参数伪装成正式 Portrait 支持。

### 受控 scale/Rank 标定结果

四张样本的 `rear.depth.config` focus 坐标分别落在 `src.image` 的 `4096×3072` storage 坐标内，而不是声明的 `900×1200` processing canvas。诊断层现在按上游的 storage-coordinate 约定，将 focus window 映射到 1024×768 rank plane，再报告 p20/p50/p80 候选值：

```text
candidateScale = focalLength * stereoBaseline
               / ((65535 - normalizedRank * rankMaximum) * objectDistance)
```

这里的 `65535`、rank-to-disparity 方向和 `objectDistance` 对齐关系都是研究假设；`fullSpanForP50` 只是 `candidateScale * 255`，不是已验证的 Apple disparity 物理量。四张样本当前得到：

| 样本 | config focus | `objectDistance` | p50 rank | `scaleForP50` | `fullSpanForP50` |
| --- | ---: | ---: | ---: | ---: | ---: |
| `IMG20260807212930` | `(2460,1410)` | 63 | 147 | 0.00445831 | 1.13687 |
| `IMG20260807212931` | `(2405,1484)` | 60 | 169 | 0.00468233 | 1.19399 |
| `IMG20260807212849` | `(1938,2012)` | 48 | 156 | 0.00585231 | 1.49234 |
| `IMG20260807212851` | `(2290,1471)` | 58 | 167 | 0.00484399 | 1.23522 |

这组结果比直接把 `0x18` 的 UInt32 原值 `4`/`6` 当作 scale 更有可比性，但样本间仍有约 `0.00446...0.00585` 的变化，尚不能证明存在一个稳定的 producer scale 公式。候选值只进入 read-only diagnostic report，生产 parser 仍拒绝 `0/0/0` quantization，`safeToTransform=false`，没有生成可宣称支持的 Portrait 输出。

验证结果：

```text
swift test                                      passed
diagnostic test with four X8U samples           passed (4/4)
classification                                  rear-v4-zero-quantization (4/4)
safeToTransform                                 false (4/4)
```

Flutter 目前只有 service/native bridge 入口，没有给用户显示 Portrait UI；下一步应把候选 scale 接入隔离的研究转换器，生成多组带不同 disparity span 的样本，再用 Apple Photos 的导入、编辑、保存、退出和重新打开行为筛选参数；在此之前不增加 Portrait capability，也不把候选值写入正式转换路径。
