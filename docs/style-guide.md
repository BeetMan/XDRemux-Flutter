# 文档写作规范

> 适用：`docs/` 下全部页面，以及提交说明、issue、PR 描述中的技术论证部分。
> 目标：让**下一个人（或下一个 agent）**在不问作者的前提下，能判断一句话是"实测结论"还是"猜测"，并能自己复现证据。
> 状态：2026-10-25 首版。与 `docs/README.md` 的「维护纪律」配套使用。

## 1. 语言与术语

### 1.1 语言

- **中文为主**，英文只用于无法翻译的标识符：盒名、字段名、API、枚举值、文件扩展名、标准编号。
- 首次出现的术语写成「中文（English）」，之后统一使用约定写法（见 1.2）。同一术语不得在同一篇里换三种叫法。
- 中文与英文/数字之间留一个半角空格：`ISO 21496-1 的 tmap item`、`SDR 8-bit`。
- 标点用全角，代码与路径用半角反引号包裹。
- 不使用 emoji 表达状态；状态用「已实测 / 推断 / 未验证」三种字样（见 §3）。

### 1.2 术语表（锁定写法）

| 约定写法 | 不要写成 | 说明 |
|---|---|---|
| gain map / 增益映射 | 增益图、gainmap（正文） | 代码标识符里的 `gainmap` 保持原样 |
| tmap | TMAP、t-map | ISO 21496-1 的元数据 item |
| 主图 | primary、主图像 | 代码里的 `primary` 保留 |
| grid / tile | 网格、切片 | 两者都在容器层出现，不要混用 |
| auxC / irot / irge / ispe / pixi | AuxC、IROT | 盒名/属性名一律小写原样 |
| ProXDR | pro-xdr、Pro XDR | OPPO 私有 HDR 表示 |
| UHDR / LHDR | U-HDR、uhdr（正文） | OPPO 两类增益映射路径 |
| Photographic Styles / 摄影风格 | 照片风格、相片风格 | Apple 功能名 |
| styleMetadata / styleData | Style Metadata | 字段名原样 |
| delta map / linear thumbnail | 差值图、线性缩略图 | 首次出现给中文注释 |
| Live Photo 配对 | 实况照片配对 | 产品文案可写「实况」 |
| content identifier | 内容标识 | `com.apple.quicktime.content.identifier` 写全 |
| Motion Photo | 动态照片 | 转换任务名 |
| FFI | ffi 层 | Dart↔Rust 边界 |
| 检查点（checkpoint） | 断点 | 队列恢复机制 |
| 队列项（queue item） | 任务、job（正文） | 代码里的 `QueueItem` 保留 |
| 上游（upstream） | 原版、官方 | 指 21Z121Z1/XDRemux；我们指 BeetMan/XDRemux-Flutter |

新增术语先加进本表，再在文档里使用。

## 2. 文档类型与目录职责

| 目录 | 放什么 | 寿命 | 必填开头 |
|---|---|---|---|
| `architecture/` | 仓库布局、数据流、平台后端、FFI 契约 | 长期 | 引用块写「先读顺序/适用改动范围」 |
| `formats/` | 对某种文件格式的逆向结论与实现约束 | 长期 | 引用块写「对应代码 + 标准依据」 |
| `modules/` | Rust 模块职责、API 面、不变量、常见坑 | 长期 | 引用块写「对应代码文件清单」 |
| `app/` | Flutter 页面/服务/模型、平台集成 | 长期 | 引用块写「涉及平台」 |
| `operations/` | 构建、发版、安装、CI、当前状态 | 长期 | 引用块写「触发条件/读者」 |
| `testing/` | 对拍套件、加用例流程、测试矩阵 | 长期 | 引用块写「覆盖范围与未覆盖项」 |
| `validation/` | 设备兼容矩阵、平台行为矩阵、一次性验证报告 | **在维护的矩阵**长期；一次性报告过期进 `archive/` | 报告首行给日期与样本 |
| `research/` | 逆向研究记录、上游对比、方案评估 | 结案后保留，结论过期标注 | 标题带日期 `name-YYYYMMDD.md`；引用块写「问题/样本/结论状态」 |
| `standards/` | 标准中译（ISO 21496-1、23008-12 等） | 长期，改动需核对原文 | 引用块写「对应标准版本/条款」 |
| `archive/` | 历史计划、已完成清单、过期验证 | 只读考古 | 首行写「历史文档，勿当现状」 |
| `plans/` | 个人/会话级计划（**在 .gitignore 中**） | 会话级 | 不作为团队事实来源 |

`plans/` 是本地草稿区：不提交、不引用为证据。要固化的计划写进 `operations/` 或 `research/`。

## 3. 证据规则（最重要）

任何技术断言必须能落进下面三类之一，并在文中标明：

| 标记 | 含义 | 必须附带 |
|---|---|---|
| **已实测** | 在本机/真机/CI 实际跑过 | 命令 + 环境（平台/版本/提交）+ 关键输出片段或文件哈希 |
| **推断** | 读代码/读标准得出，未运行 | 依据（`path:line` 或标准条款）+ 推断链一句话 |
| **未验证** | 未做或做了一半 | 缺什么、怎么补、谁负责（可选） |

禁止的写法：

- 「已验证正常」「测试通过」但没有命令、环境或输出（**CI 绿 ≠ 真机验收**，必须写清是哪一个）。
- 把 upstream 未合并分支的行为写成"上游已支持"——要写 `branch @ commit`。
- 只给结论不给样本：「部分设备不支持」应写成机型 + 系统版本 + 失败现象。
- 引用别人的结论不标出处（复制粘贴的表格也算）。

证据落点约定：

- 代码：`xdremux/rust/src/iso21496.rs:128`（仓库相对路径 + 行号；行号会漂移，允许标注"约"）。
- 提交：短哈希 + 一句话主题，如 `8844899c fix(metadata): reject reversed per-channel ISO gain ranges`。
- 文件：路径 + 大小 + SHA-256（二进制样本、构建产物必须给哈希）。
- 日志：贴**关键 5–20 行**，不要整段粘贴。

## 4. 结构模板

### 4.1 格式 / 模块文档

```markdown
# 标题

> 对应代码：`a.rs`（职责）、`b.rs`（职责）
> 标准/上游依据：`docs/standards/xxx.md` 第 N 条 / upstream `commit`

## 1. 职责与边界
## 2. 数据流（可画 ASCII）
## 3. 关键机制与不变量
## 4. 已知差异与常见坑
## 5. 验证方式（命令 + 判定标准）
```

### 4.2 验证报告（`validation/`、一次性结论）

结论先行，格式固定：

```markdown
# 主题（YYYY-MM-DD）

> 样本：机型/系统/文件（数量 + 哈希前缀）
> 结论：一句可执行的判断（通过 / 部分通过 / 未通过）

## 结论
## 证据
## 未验证与风险
```

### 4.3 研究 / 上游对比（`research/`）

```markdown
# 主题（YYYY-MM-DD）

> 问题：这次要回答什么
> 结论状态：已定论 / 推断 / 未验证
> 上游参照：`upstream/<branch>` @ `<commit>`（是否已并入 upstream/main）

## 一页结论
## 上游做法（带 commit/path）
## 我方现状（带 path:line）
## 差距矩阵（表格）
## 跟进建议（P0/P1/P2/暂不跟 + 成本 + 依赖）
## 不适用条件
```

## 5. 排版约定

- 一级标题每篇只有一个；层级不超过 `###`，再深用列表。
- 矩阵/对照一律用表格，首列是对比维度；表格里禁止塞多段文字。
- 命令用围栏代码块并标语言：`bash` / `powershell` / `rust` / `dart`。
- 交叉引用用相对路径 + 小节号：`见 docs/formats/hevc-hevc-conventions.md §4.1`。
- 大段标准原文不放正文，引用 `docs/standards/`；正文只写"标准怎么要求 + 我们怎么实现 + 偏差"。
- 数字与单位：`100000` 不写 `10 万`（避免歧义）；百分比写 `62.5%`；文件大小写 `1,518,474 字节` 或 `1.45 MiB`。
- 路径：仓库内写相对路径；本机绝对路径只在验证报告里出现，并脱敏用户名以外的隐私信息。

## 6. 双语规则

当前 `docs/` 为**单语中文**（`*.en.md` 数量为 0）。若将来要做英文版：

1. 中文先定稿，再翻译；英文文件与中文同名加 `.en.md` 后缀。
2. 术语按 §1.2 锁定，英文侧使用上游/Apple 官方英文原词。
3. 不做逐句直译：摘要、结论、命令必须重写为英文读者可执行的形式。
4. 两边不同步时，**中文为事实来源**，并在英文页首行标注 `Translation may lag behind the Chinese page.`

## 7. 提交前检查清单

- [ ] 新增/修改的页面已在 `docs/README.md` 索引里出现（新增目录要加一节）
- [ ] 断言都带 §3 的三类标记之一，且证据可复现
- [ ] 术语符合 §1.2，没有同义混用
- [ ] 表格列数一致、没有 `|` 未转义
- [ ] 引用上游时写明 `branch @ commit` 与是否已合并
- [ ] 过期内容标注日期或移入 `docs/archive/`
- [ ] `docs/` 在 `.gitignore` 中：**新文件用 `git add -f docs/<path>`**，否则不会进提交
- [ ] 涉及发版事实时对照 `tools/installer/RELEASE_NOTES_v<版本>.md` 与 `apps/flutter/pubspec.yaml`

## 8. 不适用条件

- 本规范不约束 `docs/archive/` 下的历史文档（只读，不回改）。
- 不约束 `docs/plans/`（gitignored 本地草稿）。
- 涉及标准原文时，以 `docs/standards/` 的中译为准；本标准不替代对 ISO 原文的核对。
- 若上游把 `docs/` 改为双语并给出自己的 termbase，本规范需与其对齐后重写，不能并行两套规则。
