## Phase 2：ReverseKey1 评估（研究项）

上游模型：`Models/ReverseKey1Ensemble.mlpackage`，启用方式 `XDREMUX_RESEARCH_REVERSE_KEY1_COREML_MODEL=<path>`，训练脚本 `xdremux_py/apple_reverse_key1_training.py`，Swift runtime `ReverseKey1CoreMLPredictor.swift`。

### 方案 A（先做，Mac 环境）

用上游 Swift 研究路径直接评估质量：

1. 拉上游 main（本地克隆：`../XDRemux-upstream`，本仓库无 upstream remote）
2. 在 Mac 上跑上游的 ReverseKey1 快速路径处理我们已有的 OPPO 样本集
3. 对照我们 Rust constrained solver / native 路径的输出：
   - 风格元数据结构（styles_diag 探针对比）
   - Apple 照片中的可编辑性（真机往返）
   - 端侧耗时
4. 产出评估报告（质量是否显著优于现状）

**第一、二轮结果（2026-08-25，详见 [reverse-key1-eval-20260825](../research/reverse-key1-eval-20260825.md)）**：
本机 macOS 27 需先补两个私有 API 适配才能跑通；34 张 OPPO 原生 HEIC 批量评估：
模型接受率 15%（5/34），被拒收时回落 identity、与我们的 Rust 输出等价，
接入模型路径严格不劣于现状。但准入代理依赖 Neutrino 私有 API（仅 Apple 平台），
方案 B 按原设计不可行，可行变体：仅 Apple 平台接模型路径，非 Apple 维持 identity。

### 方案 B（仅当 A 验证通过）

跨平台 Rust 推理：

1. 上游训练脚本导出 ONNX（或按模型卡手写前向：小 MLP + multiscale candidate，融合权重 0.625）
2. Rust 侧集成推理（onnxruntime 或纯 Rust 前向，注意 ONNX 模型不入 git——目前只保留本地路径引用）
3. 替换/补充 styles_native 的 key1 生成段

**验收门槛**：Apple 照片可编辑性不劣于现状 + 耗时可感知下降。达不到则停在方案 A（仅 Apple 平台研究路径）。

## Phase 3：Motion Photo / Live Photo

关键上游参考：合成顺序 = 先归一化静帧，再 Styles 增强。

- **3a（一期）**：识别 OPPO 动态照片（格式调研：Find X8 Ultra 动态照片样本，容器扩展/新 tail 条目，0.5 天调研先行）-> 提取静帧 -> 走现有管线
  - **核心已完成**：`motion_photo.rs` 移植自上游 v1.4 的 `xdremux_py/motion_photo.py`，覆盖 Android V1 / legacy MicroVideo / HEIF mpvd / OPPO LPEX 双码流；FFI `xdremux_motion_photo_inspect` / `xdremux_motion_photo_split` + Dart 绑定；6 个合成 fixture 测试全绿；Swift/Python/Rust 三方差分验证 12/12 一致（docs/research/motion-photo-parser-differential.md）
  - **UI 已完成（设计：docs/app/motion-photo-ui-design.md）**：入队即异步识别、卡片「动态」chip + 逐张三档策略菜单（跳过默认/仅静帧/静帧+视频）、设置页默认策略、工作流页 donor 自动拆静帧
  - **Ultra HDR JPEG 输入已完成（24a7a92）**：动态照片静帧是 Ultra HDR JPEG（MPF + gain map 自带 hdrgm XMP），新增 `uhdr_jpeg.rs` 合成源容器接入 UHDR 主路径；选图/拖入已放行 jpg/jpeg；5 张真实 OPPO Live Photo 全部转换成功（ISO HDR 验证通过，EDR/增益与 HEIC 管线一致）
  - 待办：真机 UI 走查；B 组带定位样本验证 GPS 透传
- **3b（二期）**：保留动态部分 + 静帧 Styles 转换 + 重组 Live Photo（参考上游合成实现）

出口：3a -> v0.4.0；3b 视反馈。
