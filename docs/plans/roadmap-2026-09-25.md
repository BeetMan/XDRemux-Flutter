### 上游的工程约束（值得对齐）

上游把「12 个语义角色共用一张 matte」明确记为**推广阻碍**：

> 发布的语义角色超出了资源能证明的语义。设备接受载体不等于声明是真的。
> 产品输出必须保留或推导有生产者依据的事实，否则省略不支持的声明或 fail closed。

同样被标记为「凭空写入」的：`HardwareModel` / `CaptureType` / `CaptureMode` / `PortType`，
以及合成的 `Apple iOS` MakerNote。**我们的实现这三点都做了**，这是真实的质量问题。

## 跨平台评估

| 组件 | 实现 | 跨平台 |
|---|---|---|
| key1 布局（多项式基 + 12 系数）| 纯 Rust | ✅ 直接可用 |
| key1 反推模型 | Core ML | ❌ 需转 ONNX 或 Rust 复现 |
| 柔肤人物 SPI | Apple 私有 | ❌ 仅作**发现层** |
| 柔肤数据契约（ROI/landmark/pose）| 数据结构 | ✅ 可 Rust 复现 |
| 人脸检测（柔肤前置）| 未定 | ⚠️ 需跨平台方案 |

**关键结论**：上游把「发现契约」和「实现契约」混在一起。发现必须在 Apple 上做
（私有 SPI 只能黑盒），但**产出这些字段的逻辑可以是纯 Rust**。

**绕过模型的路径**：如果我们只做**预设风格**（Standard/浓郁/鲜活/暖色/冷色），
可以直接用多项式基写 key1，**完全不需要模型** —— 模型只用于「从图像反推系数」。

## 优先级

### P0 —— 柔肤（当前产品里唯一"看起来坏了"的功能）
上游探针已就绪，可直接验证假设。**路线已改**：不是语义分割，而是**人脸检测 ROI**：

```
+[CMITextureStylesPersonInputDataUtilities personInputDataArrayFromDetectedFaces:]
-[CMITextureStylesProcessor setInputSkinSmoothingFaceDetections:]   ← 柔肤专用输入
```

步骤：
1. 跑上游探针（`run_texture_style_person_spi_probe.sh --all`）拿到字段语义
2. 用 trace dylib 观察真实 PhotoImaging 契约
3. Rust 复现 ROI 计算（人脸检测用 `ort` + ONNX，Apple 上可加速用 Vision）
4. 用真实人像样张验证柔肤效果

### P1 —— key1 补非 Standard 风格
1. 采用上游 `apple_style_polynomial_basis()` + 系数 delta 那套 Rust 实现
2. 预设风格（Standard/浓郁/鲜活/暖色/冷色）直接用多项式基写 key1，绕过模型
3. 需要"从图反推"时再考虑 ReverseKey1Ensemble（转 ONNX）

### P2 —— HEVC 4:4:4 解码（iPhone 截图不支持）
见 `docs/plans/sdr-decode-platform-coverage.md`：
- 阶段 1：平台解码兜底（iOS/macOS/Android/鸿蒙）
- 阶段 2：vendor `libde265`（彻底解决 + Windows）

### P3 —— provenance 对齐
容器里只写有依据的事实：
- `HardwareModel` / `CaptureType` / `CaptureMode` / `PortType` 从源推导
- 无 Apple MakerNote 时不合成（或明确标记为合成）
- 12 个语义 matte：内容与角色一致，或省略/标记

### P4 —— 其余
- Halation（无具名 kernel，需逆向）
- N3 样张纳入一致性语料

## 上游代码的使用方式：**只看不并**

仓库同步**已经不可能**（953 提交差距 + 上游重构了布局，`git merge` 无法对齐）。
不追求合并，改成**选择性移植**：

- 上游当**参考实现和契约来源**，不作为上游依赖
- 需要某块逻辑时（如 key1 多项式基、柔肤 ROI 字段），**手工移植**到我们的代码，
  并注明上游出处（commit + 文件）
- 上游的探针（`.m` + DYLD 注入）作为**研究工具**直接跑，不搬进产品代码
- 模型权重（`ReverseKey1Ensemble.mlpackage`）如需要，按 hash 引用，不当默认依赖
