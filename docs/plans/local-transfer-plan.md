# 内置局域网文件传输开发计划

日期：2026-10-17。状态：计划已建立，尚未开始实现。

## 目标与开发基线

将照片原文件可靠地传到另一台设备，减少系统分享对 HEIC、私有尾部、人像辅助图像和动态照片资源的改写。支持 XDRemux 与 LocalSend 文件互传，并为 XDRemux 间的照片资源分组和往返工作流保留扩展能力。

- 分支：`codex/local-transfer`；独立工作树开发。
- 起点：`integrate/huawei-portrait-live` 的已提交版本 `877047b87fda65ca5d8cc6bce3aa591ed1efd111`。
- 原工作区未提交的 codec、界面、网站及鸿蒙原生代码不纳入本分支。开始接入应用前，先检查这些工作是否已合入，按需更新基线。
- 本次交付仅为计划文档和索引；不新增依赖，不改图像引擎、不构建、不推送或发版。
- 技术依据为 2026-10-15 的只读调研；开始 PoC 时重新核对上游版本、协议及平台要求，并记录实际提交哈希。

## 首版范围

首版提供：发送已导入的原文件或转换结果、设备发现、手动 IP/端口、明确的接收确认、接收箱、批量进度、取消和失败文件重试。默认使用 HTTPS，接收完成后再交给转换队列或文件导出。

区分四类结果：网络传输完成、文件校验完成、图库写入完成、目标图库功能验收通过。不能用其中一项替代其他项。哈希一致只说明发送与接收字节相同，不能证明系统选择器提供的是完整原始资产。

首版不包含公网穿透、云中转、账号、目录同步、浏览器收发、通用断点续传、永久后台接收和无人确认自动接收。Live Photo 成组导入及 Apple/OPPO 往返任务关联安排在后续阶段，不作为文件互传首版的隐含承诺。

## 架构与选型原则

优先评估封装 LocalSend 独立 Rust 核心，保持 v2 文件互操作；若其嵌入、依赖或目标平台成本过高，再评估独立实现兼容协议。最终选型由 P0 的编译与互操作证据决定，不预先把仓库内部 crate 当作稳定 SDK。

建议的数据流：

`本地文件快照 → 发送会话 → 临时接收文件 → 校验与提交 → 接收箱 → 加入转换队列 / 文件导出 / 后续图库导入`

- 传输逻辑放入独立 Rust crate 候选 `crates/xdremux-transfer/`，不与 HDR、人像、编码器逻辑耦合。
- Flutter 侧采用独立服务与状态模型，避免把协议实现放进 `main.dart`；具体界面入口在 P2 确认。
- 是否复用现有动态库或单独打包，在 P0 根据可选依赖、体积与平台构建影响决定。关闭功能时不得要求图像引擎初始化网络服务。
- 延续现有 C ABI 和内存管理纪律，不为此全局迁移桥接框架。长生命周期服务使用独立 runtime/工作线程，桥接暴露短调用和有界事件队列；UI 主 isolate 不承担阻塞 I/O。
- 会话、传输和事件使用稳定 ID；定义事件顺序、取消幂等性、服务关闭、句柄释放和 ABI 版本检查。错误用稳定错误码，不依赖异常字符串匹配。
- 普通 LocalSend 对端只使用标准文件语义；XDRemux 资源分组另行协商，不能假设普通客户端理解自有清单。

## 阶段与退出条件

### P0：独立技术验证与选型

- [ ] 固定上游版本和提交；核对核心 API、依赖、Rust 工具链要求、许可证及特性开关能否实际裁剪。
- [ ] 建立不依赖图像引擎的最小收发 harness；先用手动 IP，隔离自动发现问题。
- [ ] Windows 本地双实例验证；再与官方 LocalSend 客户端双向传送 HEIC/JPEG/MOV。
- [ ] Windows/Android 验证运行；iOS/macOS/HarmonyOS 尽早验证目标编译、TLS、网卡枚举和最小直连，明确设备/签名缺口。
- [ ] 测量基线启动耗时、包体增量、吞吐、内存和 CPU；记录测试设备、网络和文件规模。
- [ ] 验证关闭传输特性时现有图像构建仍可用，传输依赖不会强制进入默认发行配置。
- [ ] 输出 `docs/research/local-transfer-poc.md`：选择复用或自实现、固定版本、兼容范围、目标编译记录、性能基线和遗留问题。

退出条件：至少 Windows 与 Android 间完成双向互传及逐文件长度/哈希比对；其他平台有明确的编译结果或可复现阻塞证据。未通过的平台列为未支持，不能因共用 Rust 逻辑标记已完成。若证据不足，继续收敛 PoC，不进入大范围 UI 接入。

### P1：可独立运行的传输服务

- [ ] 实现服务启停、地址绑定、会话协商、接收决策、逐文件发送、取消、进度和错误模型。
- [ ] 流式读写、有界并发和事件背压；不把整批文件读入内存。
- [ ] 发送前固定可读源文件快照，检查长度/修改变化；必要时复制到稳定暂存区，避免计算哈希后源文件变化。
- [ ] 接收至临时文件；检查声明长度、实际长度和可用哈希后再提交。校验失败不进入接收箱或转换队列。
- [ ] 自有客户端发送 SHA-256；接收第三方无哈希文件时记录“长度已核对、无对端哈希”，不能显示为已完成端到端哈希校验。
- [ ] 约束文件数、声明体积、元数据和路径长度；校验磁盘空间，拒绝路径穿越、绝对路径及越界链接，明确重名策略。
- [ ] 实现会话超时、取消清理、进程重启后的临时文件清理和失败文件重试。
- [ ] 默认显式接收确认；校验证书身份，禁用未经用户选择的明文降级；不把同名设备视为同一可信身份。
- [ ] 日志不记录文件内容、PIN、会话 token 和完整私人路径。

退出条件：独立 harness 通过成功、拒绝、取消、超时、空间不足、错误哈希、截断输入及路径攻击用例；重启后不会把残缺文件识别为成功文件。

### P2：Flutter 文件互传首版

- [ ] 新建传输服务、设备/会话/文件状态模型和接收箱持久化；定义正在接收与可用文件的边界。
- [ ] 接入“发送原文件/发送转换结果”和“接收文件”入口；展示设备、文件数、体积及目标保存位置。
- [ ] 支持手动 IP/端口；设备发现失败与连接失败分别呈现可操作错误。
- [ ] 支持总进度、逐文件状态、拒绝、取消、失败重试和“加入转换队列”；文件格式按队列现有导入规则校验。
- [ ] 只在用户启用接收或主动发送时启动网络功能；定义离开页面、退后台、停止接收和退出应用时的生命周期。
- [ ] 接收箱有空间提示、保留与清理操作；导入队列后不能因清理导致正在使用的文件消失。
- [ ] 按现有项目方式实现中英文文案、错误映射和桌面/移动端布局。

退出条件：Windows/Android 应用端完成完整收发闭环；含私有尾部 HEIC 与多文件批次字节一致，转换回归通过；取消、重试和清理不会破坏源文件或已有输出。

### P3：平台适配与互操作验收

- [ ] iOS：本地网络用途声明与授权；核对 multicast entitlement 和实际签名可用性。不可用时保留手动直连并说明自动发现限制。
- [ ] iOS：按前台传输设计，验证锁屏、切后台、网络切换和恢复；不得将普通 Rust socket 当作系统后台传输。
- [ ] Android：按实际 target SDK 核对 INTERNET、局域网访问、多播与前台任务策略；SDK 升级时复核权限变化。
- [ ] Windows/macOS：网络权限、防火墙、VPN、多网卡和 IPv4/IPv6 行为；仅公告可实际连接的地址。
- [ ] 与 LocalSend 同时运行：检测端口占用，支持其他监听端口，验证公告和直连。手动 IP 不能绕过 AP 隔离或防火墙。
- [ ] HarmonyOS Flutter：通过 `devecocli` 验证构建、设备运行、TCP/TLS、多播、文件访问及生命周期；原生 ArkUI 接入在其开发分支协调。
- [ ] 固定版本与实施时选定的旧版本 LocalSend 双向验收，分别记录发送/接收方向和平台。

退出条件：拟宣称支持的平台都有真机/桌面运行记录；签名、设备或网络条件缺失的项保持待验收。按平台开放功能，不用单平台结果代表五平台完成。

### P4：照片资源分组与图库流程

- [ ] 设计并版本化 XDRemux 能力协商与资源清单，记录资源组、静帧/视频角色、长度、哈希及可选工作流 ID。
- [ ] HEIC + MOV 保持现有配对标识；整组到齐且校验成功后才允许 Live Photo 导入。
- [ ] 苹果端复用或协调独立 Live Photo 导出分支的实现；先核对已有工作，避免重复改 Photos 桥接。
- [ ] 普通文件和图库资产操作分别报告结果，图库失败时保留已接收文件供重试。
- [ ] Apple/OPPO 回传分别定义渲染成片、原始文件和完整编辑资源的语义，再接工作流 ID，不通过文件名猜测 donor。

退出条件：配对缺失、哈希失败和取消均不会创建半成品图库资产；实际 iPhone 验证实况、声音及匹配照片能力。HDR/人像/摄影风格的兼容性按样片记录，不能从传输成功推断。

### P5：集成、文档与发布准备

- [ ] 更新 FFI 契约、平台构建说明、用户操作与排障文档，分发所需第三方许可。
- [ ] 将涉及的主线接口变动合入或重放后，运行受影响的 Rust、桥接、Flutter 和平台构建检查。
- [ ] 检查功能开关、依赖体积、启动性能与原有导入/转换/分享回归。
- [ ] 完成下述验收矩阵并记录已支持平台、明确限制和待验证项。

退出条件：拟发布范围的验证全部通过，结果可追溯。发布、推送及合并另按当时任务安排执行，本计划不触发这些操作。

## 验收矩阵与证据

| 维度 | 最低覆盖 | 证据 |
|---|---|---|
| 文件保真 | JPEG、普通 HEIC、带私有尾部/人像数据 HEIC、MOV、正确 Live Photo 双文件 | 两端长度与 SHA-256；输入文件保持不变 |
| 批次与性能 | 单文件 ≥2 GiB、至少 1000 个小文件、照片混合批次 | 文件清单、用时、峰值内存/CPU和网络信息；文件增大时内存不按文件大小线性增长 |
| 生命周期 | 取消、退出、进程被杀、锁屏、退后台、网络断开/切换、恢复重试 | 文件与会话终态、临时文件清理、重复/覆盖行为 |
| 文件系统 | 中文、emoji、重名、路径边界、磁盘不足、无权限 | 错误码与用户提示；既有文件不被意外覆盖 |
| 网络与权限 | 权限拒绝/撤销、VPN、多网卡、端口冲突、多播失败、AP 隔离 | 发现/直连分别记录，失败原因与兜底路径 |
| 互操作 | XDRemux ↔ XDRemux；XDRemux ↔ 选定 LocalSend 版本 | 双方向、平台/客户端版本、文件清单和校验结果 |
| 图库与回归 | 文件保存、后续 Live Photo 导入、现有转换和系统分享 | 分开记录传输与图库结果；真实目标图库验证 |

测试分层：Rust 覆盖会话、流式写入、路径/体积约束、校验和取消；桥接覆盖句柄释放、事件顺序及并发；Flutter 覆盖接收确认、进度、重试和队列交接；真实设备负责权限、多播、后台限制、跨客户端及图库行为。性能阈值在 P0 测量后确定，不使用未经测量的速度承诺。

建议验证记录落在 `docs/testing/local-transfer-validation.md`，以“未执行/通过/失败/受阻”记录每项，不以文档存在代表验证通过。

## 第一轮执行顺序

1. 完成 P0：锁定上游、建立独立 harness、Windows/Android 双向互传，尽早排查 Apple 与鸿蒙目标。
2. 根据 P0 证据定核心复用与 ABI 方案，再实施 P1。
3. 先完成 P2 的文件收发闭环，再收敛 P3 各平台体验。
4. 协调已有 Live Photo 与鸿蒙原生开发后推进 P4；最后完成 P5。
