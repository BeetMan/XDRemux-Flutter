# v0.4.2 计划：全量重转 + 任意照片风格附加

> 背景：PS3 契约（styles + texture_styles + 12 matte + maker note）在
> OPPO 转换产物和 Apple 原生照片上实机验证通过；但在第三方容器
> （华为 HEIC）上做原位 Exif/TIFF 重建会让 Photos 崩溃（Z5/Z6/hw 实验），
> 且 16e 本机拍摄的照片疑似有资产来源级门禁。
> 结论：放弃第三方容器的原位附加，改为**全量重转**——所有输入统一走
> 解码 → x265 编码 → 标准容器构建 → 契约注入，产出与已验证格式同源。

## 路线

### Phase 2a：HEIC/HEIF 输入的全量重转
1. **解码**：输入 HEIC → RGB 帧。选项：
   - Flutter 侧解码（平台 ImageIO/MediaCodec）→ RGBA bytes → FFI 传入；
   - 或 Rust 侧接入 img/ libheif-rs（评估体积与平台支持）。
   建议 Flutter 侧解码（零新原生依赖，三端行为一致）。
2. **编码**：现有 `x265_encode_tiles`（HDR 输入可带增益图走完整管线）。
3. **容器构建**：新增 `container_build.rs` —— 从 RGB/增益帧构建标准 HEIC
   （grid + tmap + Exif 透传 + 尺寸/属性），复用 portrait_scaffold 的
   容器组装零件。
4. **契约注入**：现有 `styles_native` + `inject_texture_styles` +
   `inject_semantic_mattes` + maker note（scaffold 管线，已实机验证）。

### Phase 2b：JPEG 输入
- `jpeg_decode.rs` 已有解码；同 2a 的编码/构建/注入链路。

### 过渡态（已实现，随本提交）
- styles-attach 对「无 MakerNote 的 HEIC」保持干净附加（实机验证路径）；
- 对「已有 MakerNote 的输入」（原生相机/厂商 note）**跳过** maker note
  合并——原位替换产出会让 Photos 崩溃的文件（Z5/Z6/hw 实验实证），
  该类输入等 Phase 2a 全量重转。

## 已验证事实（勿重复实验）
- 契约本身（styles + texture_styles + 12 matte 占位）在 Apple 容器上
  解锁质感/胶片/颗粒/光晕（V 实机）；柔肤需真实 skin mask。
- maker note 是风格编辑总开关（X 实验：剥离即全部消失）。
- 原位 TIFF 重建（即使 exiftool/sips 通过）会让 Photos 崩溃
  （重复 0x927c、type7 尺寸、字节序均已修复仍崩——Apple 语义更严）。
- 16e 本机拍摄照片：疑似资产来源级门禁，文件级无解（Z1-Z6 全败）。
