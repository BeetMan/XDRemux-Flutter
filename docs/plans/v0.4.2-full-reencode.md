# v0.4.2 计划：全量重转 + 任意照片风格附加

> 背景：PS3 契约（styles + texture_styles + 12 matte + maker note）在
> OPPO 转换产物和 Apple 原生照片上实机验证通过；但在第三方容器
> （华为 HEIC）上做原位 Exif/TIFF 重建会让 Photos 崩溃（Z5/Z6/hw 实验），
> 且 16e 本机拍摄的照片疑似有资产来源级门禁。
> 结论：放弃第三方容器的原位附加，改为**全量重转**——所有输入统一走
> 解码 → x265 编码 → 标准容器构建 → 契约注入，产出与已验证格式同源。

## 路线

### Phase 2a：HEIC/HEIF 输入的全量重转
1. **解码**：输入 HEIC → RGB 帧。选项：
   - Flutter 侧解码（平台 ImageIO/MediaCodec）→ RGBA bytes → FFI 传入；
   - 或 Rust 侧接入 img/ libheif-rs（评估体积与平台支持）。
   建议 Flutter 侧解码（零新原生依赖，三端行为一致）。
2. **编码**：现有 `x265_encode_tiles`（HDR 输入可带增益图走完整管线）。
3. **容器构建**：新增 `container_build.rs` —— 从 RGB/增益帧构建标准 HEIC
   （grid + tmap + Exif 透传 + 尺寸/属性），复用 portrait_scaffold 的
   容器组装零件。
4. **契约注入**：现有 `styles_native` + `inject_texture_styles` +
   `inject_semantic_mattes` + maker note（scaffold 管线，已实机验证）。

### Phase 2b：JPEG 输入
- `jpeg_decode.rs` 已有解码；同 2a 的编码/构建/注入链路。

### 过渡态（已实现，随本提交）
- styles-attach 对「无 MakerNote 的 HEIC」保持干净附加（实机验证路径）；
- 对「已有 MakerNote 的输入」（原生相机/厂商 note）**跳过** maker note
  合并——原位替换产出会让 Photos 崩溃的文件（Z5/Z6/hw 实验实证），
  该类输入等 Phase 2a 全量重转。

## 最终根因（2026-09-16 凌晨确认）

**styles 编辑器需要完整的 styles scaffold**（styledeltamap + linear thumbnail +
sky matte），不只是元数据项。OPPO 转换管线自动生成这些伴随结构（scaffold()），
所以 V 文件能用。非 OPPO 容器没有这些结构 → 注入元数据项后 Photos 崩溃。

### 证据
- V（OPPO 转换 + 全套契约）：✓ 可用（scaffold 完整）
- H-st/H-tm/H-sm（华为 + 无 note 的部分注入）：不崩但不可用（无 scaffold）
- Z5/Z6/hw-final（+ note 但无 scaffold）：崩溃（Photos 试图使用不存在的 scaffold）
- sdr-styles（synthesize + 全套契约但无 scaffold）：崩溃（同上）

### 解法
非 OPPO 照片 → 合成最小 tmap + 增益 grid → 走 styles_native 全管线
（自动生成 styledeltamap/linear thumbnail/sky matte/styles 项）→ PS3 注入。

需要改 scaffold() 接受无增益图的 SDR 输入（SDR 分支跳过增益图步骤）。

### 下轮实施步骤
1. scaffold() 加 SDR 分支：无 tmap/增益 grid 时跳过增益图相关步骤，
   保留 primary grid + styles scaffold 生成
2. SDR 输入（JPEG 解码 → RGB → tiles）→ scaffold → styles_native → PS3 注入
3. 实机验证

## ✅ 实机验证（2026-09-16）

**任意照片输入 → 摄影风格 3 功能完整实现并实机验证可用。**

用户确认：华为 HEIC（此前一直失败的案例）+ Apple SDR 派生图，两张均「功能已实现」。

### 最终方案

不再往外来容器上嫁接元数据项（那会崩溃），而是**重建标准容器**：

```
任意输入（HEIC/JPEG/PNG…）
→ Flutter 平台编解码器解码 → RGBA
→ Rust xdremux_convert_sdr_rgba
   → 丢弃 alpha → RGB
   → synthesize_source_container_from_rgb（标准 HEIC：primary grid + tiles + Exif）
   → 恒等增益图 + 中性 meta_floats（extracted.mode = "uhdr"）
   → 未改动的转换管线 → tmap + 增益 grid + styledeltamap
      + linearthumbnail + skymatte + styles 项
→ PS3 契约（texture_styles + 12 matte）
→ 输出
```

### 为什么之前失败

| 方案 | 结果 | 原因 |
|---|---|---|
| 原位注入契约项到外来容器 | 不崩但无风格 / 崩溃 | 缺 styles scaffold |
| ImageIO 重编码 + 注入 | 崩溃 | 同上，且 maker note 合并破坏 TIFF |
| **重建标准容器** | ✅ **可用** | scaffold 完整生成，结构与 OPPO 产物一致 |

### 关键实现点

- `synthesize_source_container_from_rgb`（从 UHDR 路径重构）—— 容器构建复用已验证代码
- `styles_attach::extract_exif_tiff` —— 保留原图 Exif（已验证：HUAWEI Pura X View + 拍摄时间）
- Flutter 解码在主 isolate（`ui.Image` 不可跨 isolate），只把像素 buffer 传进转换 isolate
- iOS 需 `-Wl,-u,_xdremux_convert_sdr_rgba`（dead-strip 保留符号）
- 无 Apple 框架依赖：解码走 Flutter 平台编解码器（跨平台），核心逻辑全在 Rust

### 遗留

- 柔肤需真实皮肤分割 mask（当前 no-op）
- 非 Standard 风格的 key1 lattice
- Halation 实现

## ✅ app 端到端实机验证（2026-09-16，v0.4.2 build 36）

用户确认：华为 HEIC + iPhone 16e 自拍，在 app 内转换后**摄影风格 3 均成功、验证可用**。

这是完整链路（Flutter 平台解码 → RGBA → Rust 重建容器 → scaffold → PS3 契约）
的首次端到端实机通过 —— 此前只验证过 CLI 路径。

### 端到端踩到的两个坑（已修）

1. **源 MakerNote 必须剥离**
   - 华为：Exif 里有两个 `0x927c` 条目 → 管线 Exif 重写报 `duplicate exif tag`
   - 16e：Apple MakerNote 不完整且带不透明 out-of-line UNDEFINED 载荷 →
     `cannot expand Apple MakerNote with unknown out-of-line UNDEFINED payload`
   - 修法：`styles_attach::strip_note_from_tiff()`，携带 Exif 前剥离，
     scaffold 重新合成完整模板（不再 merge）

2. **方向必须归一化**
   - 平台解码器（Flutter/Skia、ImageIO、MediaCodec）解码时已应用 EXIF 方向，
     但携带的原图 Exif 仍带 Orientation → 查看器二次旋转
   - 修法：`exif::normalize_tiff_orientation()`，把携带的 IFD0 Orientation 置 1
   - 验证：16e 3088×2316 Rotate90CW → 2316×3088 Normal；
     华为 4320×5760 Normal 不变

### 关键教训

CLI 路径（Rust 自己解码 JPEG）与 app 路径（平台解码 + Rust 收像素）
**输入形态不同，会暴露不同的 bug**：
- CLI 的 JPEG 由 `sips` 生成，Exif 已被重写（无重复条目）
- app 传的是原图 Exif（含厂商脏数据）
- CLI 的像素未旋转，app 的像素已旋转
→ 测试必须模拟 app 的确切输入形态（像素已旋转 + Exif 来自原文件），
  见 `examples/sdr_rgba_test.rs`
