# v0.4 路线图（参考上游 XDRemux 同步）

> 制定时间：2026-08。上游参照：21Z121Z1/XDRemux main（`af6e448`，132 个新提交后的快照）。
> 排序原则：已有功能正确性闭环 > 新功能；跨平台一致性（Rust 主路径）优先，Apple 原生路径保持研究性质；上游成果只在可验证前提下引入。

## 上游增量信号（2026-08 同步）

| 上游工作 | 要点 | 对我们的价值 |

## Phase 2：ReverseKey1 评估（研究项）

上游模型：`Models/ReverseKey1Ensemble.mlpackage`，启用方式 `XDREMUX_RESEARCH_REVERSE_KEY1_COREML_MODEL=<path>`，训练脚本 `xdremux_py/apple_reverse_key1_training.py`，Swift runtime `ReverseKey1CoreMLPredictor.swift`。

### 方案 A（先做，Mac 环境）

用上游 Swift 研究路径直接评估质量：

1. 拉上游 main（本地克隆：`../XDRemux-upstream`，本仓库无 upstream remote）
2. 在 Mac 上跑上游的 ReverseKey1 快速路径处理我们已有的 OPPO 样本集
3. 对照我们 Rust constrained solver / native 路径的输出：
   - 风格元数据结构（styles_diag 探针对比）
   - Apple 照片中的可编辑性（真机往返）
   - 端侧耗时
4. 产出评估报告（质量是否显著优于现状）

**第一轮结果（2026-08-25，详见 [reverse-key1-eval-20260825](../research/reverse-key1-eval-20260825.md)）**：
本机 macOS 27 需先补两个私有 API 适配才能跑通；模型快速路径 3.9–5.4s（solver 22s）
已验证，但我方 OPPO 样本被语义代理拒收回落 identity（与我们的 Rust 输出等价），
质量门槛未证。下一步是扩充 OPPO 多样本集再测接受率。

### 方案 B（仅当 A 验证通过）

跨平台 Rust 推理：

1. 上游训练脚本导出 ONNX（或按模型卡手写前向：小 MLP + multiscale candidate，融合权重 0.625）
2. Rust 侧集成推理（onnxruntime 或纯 Rust 前向，注意 ONNX 模型不入 git——目前只保留本地路径引用）
3. 替换/补充 styles_native 的 key1 生成段

**验收门槛**：Apple 照片可编辑性不劣于现状 + 耗时可感知下降。达不到则停在方案 A（仅 Apple 平台研究路径）。

## Phase 3：Motion Photo / Live Photo

关键上游参考：合成顺序 = 先归一化静帧，再 Styles 增强。

- **3a（一期）**：识别 OPPO 动态照片（格式调研：Find X8 Ultra 动态照片样本，容器扩展/新 tail 条目，0.5 天调研先行）-> 提取静帧 -> 走现有管线
- **3b（二期）**：保留动态部分 + 静帧 Styles 转换 + 重组 Live Photo（参考上游合成实现）

出口：3a -> v0.4.0；3b 视反馈。
